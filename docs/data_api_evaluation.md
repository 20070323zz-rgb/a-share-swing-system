# 长期稳定数据 API 评估

资料日期：2026-06-07

本文只评估 ETF 历史日线与近期行情更新的数据来源，不评估、不设计、不接入任何交易能力。

## 方向更新：东方证券 QMT / miniQMT 只读行情试点

用户开户券商为东方证券。当前新增一个受限评估方向：重点评估东方证券 QMT / miniQMT 的 `xtquant.xtdata` 只读行情能力。

该方向只允许进入 staging 试点，不改变项目安全边界：

1. 不接交易 API。
2. 不使用 `xttrader`。
3. 不读取资金账户。
4. 不查持仓。
5. 不保存账号密码。
6. 不真实下单。
7. 不自动交易。
8. 不写入 `data/etf_daily/`。

具体计划见：`docs/qmt_readonly_data_plan.md`。

## 当前项目边界

本项目可以做的事情：

1. 评估只读行情 API。
2. 读取用户手动放入本地的 CSV。
3. 在用户确认数据权限后，编写只读行情下载脚本。
4. 将外部数据标准化为 `date,open,high,low,close,volume`。

本项目明确不做的事情：

1. 不接交易 API。
2. 不读取资金账户。
3. 不保存账号、密码、cookie、token 或券商登录信息。
4. 不自动交易。
5. 不真实下单。
6. 不把任何交易客户端当作系统依赖。

## 评估结论摘要

若用户能获得学校或机构数据库权限，长期主历史源应优先选择学校数据库导出的 CSV，尤其是 Wind、Choice、iFinD 或 CSMAR。它们的稳定性、可追溯性和数据完整性通常优于免费公开接口，但自动化程度取决于学校是否允许 API、批量导出和校外访问。

若用户暂时没有机构权限，BaoStock 和东方财富公开接口可以作为短期可用的数据来源，但不能把东方财富公开接口视为长期稳定主源；BaoStock 更适合继续做本机验证和备用补洞，前提是确认 76 个 ETF 的覆盖率。

券商只读行情 API 可以评估，但当前项目不建议接入。原因不是行情本身不可用，而是券商 API 往往与交易客户端、交易账号、下单模块或账户环境绑定，容易越过本项目的安全边界。

## 分项评估

### 1. 同花顺 iFinD 数据接口

定位：专业金融数据库的数据接口，适合有权限的个人、私募、学校或机构用户。

优点：

1. 支持 Python、HTTP 等程序化接口，适合本机终端调用。
2. 数据品类覆盖面广，ETF 历史日线、宽基 ETF、行业 ETF 支持概率高。
3. 适合作为长期主历史源和盘后近期更新源。
4. 可以保持只读行情，不需要交易账户。

风险与限制：

1. 获取权限不如免费接口容易，通常需要试用、购买或机构权限。
2. 可能有数据量、并发、字段权限和品种权限限制。
3. 项目不能保存 iFinD 账号密码；如果未来接入，只能采用用户本机环境变量、系统钥匙串或人工登录后的只读运行方式。

适配建议：

1. 若用户已有 iFinD 权限，优先做只读 ETF 日线验证脚本。
2. 先验证 76 个 ETF 的 `date,open,high,low,close,volume,amount` 覆盖情况。
3. 不把账号写入配置文件，不提交任何凭据。

### 2. 券商只读行情 API

定位：券商客户端或量化平台提供的行情查询能力，例如 QMT、Ptrade 或券商自有 API。

优点：

1. 多数券商量化环境支持历史 K 线、实时行情、ETF、批量查询。
2. 行情与交易市场连接较近，近期更新通常较快。
3. 技术上可以只调用行情模块，不调用下单模块。

风险与限制：

1. 常与交易账号、交易客户端、资金账号或柜台权限绑定。
2. 同一套 SDK 里可能同时存在行情函数和交易函数，项目治理风险高。
3. 即使只读，也容易引入登录态、账号信息、客户端依赖和误用风险。

适配建议：

1. 当前项目不接入券商 API。
2. 允许用户把券商软件手动导出的 CSV 放入 `raw/` 后导入。
3. 若未来重新讨论，只能考虑完全隔离的只读行情模块，并且必须先更新项目安全边界。

### 3. 学校数据库导出 CSV

定位：用户通过学校图书馆、实验室或数据库平台导出 ETF 历史日线 CSV，再交给本项目标准化。

优点：

1. 不需要项目连接任何外部账号系统。
2. 不涉及交易账户。
3. 数据来源可追溯，适合作为主历史源。
4. 与当前项目的本地 CSV 架构最匹配。

风险与限制：

1. 自动化程度低，近期更新依赖用户手动导出。
2. 批量导出能力取决于数据库平台和学校权限。
3. 不同数据库导出的字段名、复权方式、成交量单位可能不同，需要导入校验。

适配建议：

1. 推荐作为第一优先级确认。
2. 先让用户导出 3 个样例 ETF：`510300`、`159915`、`512880`。
3. 确认日期格式、复权方式、成交量单位、是否含成交额。
4. 确认后再批量导出 76 个 ETF。

### 4. Wind / CSMAR / Choice / iFinD 学校权限

定位：学校或机构采购的专业金融数据库权限。

优点：

1. 数据质量和长期稳定性通常最好。
2. Wind、Choice、iFinD 常见于终端和 API 场景；CSMAR 常见于研究数据库、API 和 CSV 导出。
3. 支持 ETF 历史日线、宽基 ETF、行业 ETF 的概率高。
4. 不涉及交易账户，可严格只读。

风险与限制：

1. 学校权限可能限制登录地点、并发、导出条数、API 使用、校外访问或商用用途。
2. 不同学校订阅的数据库模块不同，不能假设 ETF 数据一定完整。
3. API 权限和终端权限可能是两件事：能打开终端不等于能用 Python API。

适配建议：

1. 优先确认学校是否有 Wind、Choice、iFinD 或 CSMAR。
2. 优先使用 CSV 导出，除非学校明确允许 API。
3. 如果可使用 API，再做只读下载器；如果只能馆内终端使用，则继续走手动 CSV 导入。

### 5. BaoStock

定位：免费 Python 数据接口，适合本机低频历史行情下载和备用补洞。

优点：

1. 获取门槛低，通常不需要账号。
2. 支持 Python，和当前项目兼容。
3. 不涉及交易账户，可以保持只读。
4. 适合做备用源和覆盖率验证。

风险与限制：

1. ETF 覆盖可能不完整，尤其是行业 ETF、跨境 ETF、较新的 ETF。
2. 免费源没有机构级服务承诺。
3. 数据字段、停牌、成交量单位、复权方式需要逐只校验。

适配建议：

1. 保留 BaoStock 作为本机验证和备用补洞源。
2. 不在 76 个 ETF 覆盖率确认前把它升级为唯一主历史源。
3. 继续生成覆盖率报告和健康检查报告。

### 6. 东方财富公开接口

定位：公开网页接口或被第三方库封装的行情路径，适合低成本获取近期和历史 K 线。

优点：

1. 获取门槛低，通常不需要账号。
2. 支持 Python HTTP 调用。
3. 对 ETF 日 K、宽基 ETF、行业 ETF 支持概率较高。
4. 不涉及交易账户。

风险与限制：

1. 不是面向本项目承诺的正式数据 API 合约。
2. 字段、参数、域名、限流、反爬或返回格式可能变化。
3. 当前用户已明确不要继续修东方财富接口，因此不应继续投入主线开发时间。

适配建议：

1. 不再把东方财富公开接口作为主修方向。
2. 保留为可选备用源或人工导出来源。
3. 若已有脚本可用，可以低优先级保留；若失效，不继续深修。

## 推荐优先级

### P0：先确认学校或机构数据权限

推荐顺序：

1. 学校数据库导出 CSV。
2. Wind / Choice / iFinD / CSMAR 学校权限。
3. 同花顺 iFinD 数据接口个人或机构权限。

原因：

1. 最适合作为长期主历史源。
2. 数据可追溯，稳定性最好。
3. 可以完全避开交易账户和交易 API。
4. 与本项目本地 CSV 架构兼容。

### P1：保留 BaoStock 作为本机免费备用源

BaoStock 适合继续用于：

1. 免费数据补洞。
2. 本机批量覆盖率验证。
3. 与学校 CSV 或 iFinD 数据做交叉校验。

不建议在未完成 76 个 ETF 覆盖率验证前，把 BaoStock 设为唯一主历史源。

### P2：东方财富公开接口降级为备用

东方财富公开接口适合：

1. 临时拉近期数据。
2. 作为某些 ETF 的备用补洞。
3. 和其他源做价格交叉校验。

不适合继续作为当前主线开发方向，也不适合作为长期稳定主历史源。

### P3：券商只读行情 API 只评估，不接入

券商只读行情 API 暂时只保留在评估层：

1. 不写券商 API 连接代码。
2. 不读取券商账号。
3. 不接入交易客户端。
4. 不保存登录信息。
5. 不把券商接口放入自动任务。

## 下一步需要用户确认的问题

1. 你是否有学校图书馆、实验室或机构数据库权限？如果有，具体是 Wind、CSMAR、Choice、iFinD 还是其他平台？
2. 学校数据库是否允许导出 ETF 历史日线 CSV？是否允许批量导出 76 个 ETF？
3. 导出数据是否可以选择前复权、不复权、成交量单位和成交额字段？
4. 是否允许 Python API 调用？如果允许，是本机可用，还是只能在学校机房/远程桌面内使用？
5. 你希望主历史源采用哪种复权口径：不复权、前复权，还是同时保留两份？
6. 76 个 ETF 的最终名单是否已经固定？如果未固定，应先冻结 `watchlist.csv` 的 ETF 池再批量建库。
7. 对近期更新的可接受延迟是多少：收盘后当天、T+1，还是每周更新一次即可？
